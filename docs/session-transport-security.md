# 인터랙티브 세션 전송 구간 보안 — 결정 기록

작성 2026-08-06 · 대상 SCR-06 (U-IA-02) 원격 데스크톱/ParaView 세션

> **결론**: 로그인 노드 → 워커 구간이 평문인 상태를 **현재 방식대로 유지한다.**
> 지금은 두 노드가 같은 기계라 실제 노출이 없고, 이 클러스터는 이미 "내부망을
> 신뢰한다"는 전제 위에 서 있다(`/home`이 NFSv3 `sec=sys`). **아래 재검토 조건 중
> 하나라도 성립하면 다시 판단한다.**

---

## 1. 경로별 방어선

세 갈래가 서로 다른 문을 맡는다. 섞어서 이해하면 판단을 그르친다.

| 구간 / 문 | 방어 |
|---|---|
| 브라우저 → 백엔드 | WSS(TLS) |
| 백엔드 → 로그인 노드 | SSH |
| **로그인 노드 → 워커:5901** | **없음(평문)** ← 이 문서의 주제 |
| 워커 로컬 X 소켓 | MIT-MAGIC-COOKIE (`Xvnc -auth`, 이미지 1.5부터) |
| 워커 5901 접속 인증 | 세션별 랜덤 VNC 비밀번호 (VncAuth) |

`--exclusive`는 **여기 어디에도 속하지 않는다.** 자원 스케줄링 옵션이다.
(1.4까지는 X 쿠키가 없어 결과적으로 유일한 방어선처럼 보였지만, 인과가 뒤바뀐 상태였다.)

## 2. 수용하는 위험

노드가 분리되고, 그 구간을 관찰할 수 있는 위치가 존재할 때 성립한다.

| 성격 | 내용 |
|---|---|
| 기밀성 | 프레임버퍼(=화면)와 `KeyEvent`(=키 입력)를 **인증 없이 관찰만으로** 읽힘 |
| **무결성** | **키 입력 주입 가능.** 보는 것이 아니라 조작하는 것 — 성격이 다르다 |
| 자격증명 | VncAuth(DES 챌린지-응답) 캡처 → 오프라인 대입 → 세션 잠입 |

- RFB 인증은 **접속 시 1회**다. 비밀번호는 *들어오는 것*을 막지 *들여다보는 것*을 막지 않는다.
- Xvnc의 `UseBlacklist=on` / `BlacklistThreshold=5`(기본값)는 **온라인 시도에만** 걸린다.
  오프라인 대입에는 무관하다. 8자 영숫자(62⁸≈2.2×10¹⁴)는 DES 연산이 빨라
  **GPU 한 장 기준 수 시간 규모로 추정**한다 — "수십 년"이 아니다.
- `-AlwaysShared`라 비밀번호를 얻은 자가 붙어도 **사용자를 밀어내지 않고 조용히 같이 본다.**
- **완화 요소**: 비밀번호가 세션마다 새로 발급되므로 깨도 그 세션 하나뿐이다.

공격 위치는 "인터넷 아무나"가 아니다. 침해된 노드·스위치 접근 권한자·내부자 등
**클러스터 내부 경로에 이미 자리를 잡은 쪽**이다.

## 3. 지금 문제가 아닌 이유

**로그인 노드와 워커가 같은 기계다.** 그 트래픽은 loopback에서만 돌고 네트워크에
나가지 않는다. 지금 상태는 위험 수용이라기보다 **판단 유예**에 가깝다.

## 4. 판단 근거 — 내부망 신뢰는 이미 서 있는 전제다

dev01에서 확인한 `/home` 마운트:

```
198.19.64.8:/scp_users_tl8g1s on /home type nfs (vers=3, proto=tcp, sec=sys, ...)
```

**NFSv3 + `sec=sys`** — 인증도 암호화도 없다(클라이언트가 주장하는 UID를 그대로 믿는다).
같은 네트워크 위치의 공격자는 **이미 사용자 홈 디렉터리를 평문으로 읽고 쓸 수 있다.**

여기서 두 가지가 따라온다.

1. VNC 평문 구간은 **새로운 종류의 노출이 아니다.** 같은 전제에서 이미 더 큰 문이 열려 있다.
2. 따라서 **VNC만 SSH로 감싸는 것은 보안 효과가 거의 없다.** 그 공격자는 NFS로 데이터를
   가져간다. 내부망을 못 믿게 되는 날에는 NFS(krb5p 등)까지 **함께** 다뤄야 한다.

이 결정은 클러스터의 기존 전제와 **일관된** 것이지, 전제를 새로 깎아내리는 것이 아니다.

## 5. 재검토 조건

하나라도 성립하면 이 문서를 다시 연다.

1. **로그인 노드와 워커가 다른 기계로 분리**될 때 (가장 가능성이 높다)
2. 클러스터에 **규정·계약상 기밀 요구가 있는 데이터**가 올라올 때
3. 내부망에 **신뢰하지 않는 테넌트**가 들어올 때

## 6. 착수하게 되면 — 해법과 걸림돌

### 해법: SSH를 워커까지 한 홉 연장

지금도 SSH 터널링이다([backend/app/clients/ssh/tunnel.py](../backend/app/clients/ssh/tunnel.py)).
로그인 노드에 SSH로 붙어 `direct-tcpip` 채널을 여는데, 그 채널의 목적지를 로그인 노드의
sshd가 **평문 TCP로** 연결한다. 그 두 번째 구간을 SSH로 바꾼다.

```
지금:  포털 ──SSH──> 로그인 노드 ──평문 TCP──> 워커:5901
제안:  포털 ──SSH──> 로그인 노드 ──SSH──> 워커 ──> 127.0.0.1:5901

CLI 등가:  ssh -J svc@login svc@worker -L 5901:127.0.0.1:5901
```

구현은 로그인 노드 채널 위에 **두 번째 paramiko Transport를 얹어** 워커에 인증하고,
거기서 다시 `direct-tcpip`으로 `127.0.0.1:5901`을 여는 형태다(SSH 안에 SSH).

**부수 효과가 크다** — Xvnc를 `-localhost yes`로 묶을 수 있어 **5901 포트가 네트워크에서
아예 사라진다.** 스캔·스푸핑이 붙을 대상 자체가 없어지고 방화벽 규칙도 불필요하다.

### 대가

- 포털이 **워커 노드에도 SSH로 닿게 된다.** 지금은 로그인 노드 한 대만 신뢰하면 되는데
  그 범위가 계산 노드 전체로 넓어진다 — 포털 키 유출 시 피해 범위가 커진다.
  이는 [plan.md](plan.md) §4.1의 "로그인 노드 자격증명만 보유" 전제를 조정한다는 뜻이다.
- 세션 접속마다 SSH 핸드셰이크가 2회다. 접속 시점 한 번이고 스트림 자체는 영향 없다.

### 제일 먼저 막힐 지점: `pam_slurm_adopt`

계산 노드 sshd에 이게 걸려 있으면 **그 노드에 Job이 없는 사용자의 SSH를 거부**한다.
포털 서비스 계정은 워커에 Job이 없으니 그대로 막힌다. HPC에서 표준적인 설정이라
**착수 전에 워커의 `sshd_config`와 `pam.d/sshd`부터 확인해야 한다.**

우회는 둘.

- 서비스 계정을 `pam_slurm_adopt` 허용 목록에 예외로 둔다.
- **두 번째 홉을 세션 소유자 계정으로 붙는다.** 그 사용자는 해당 노드에 Job이 있으니
  통과한다. 로그인 노드에서 이미 `sudo -u <user>`를 쓰고 있어 흐름도 자연스럽다 —
  이쪽이 더 깔끔해 보인다.

인증 방식은 키(서비스 계정 공개키를 워커 `authorized_keys`에) 또는 hostbased
(워커가 로그인 노드를 신뢰, MPI용으로 이미 깔린 클러스터가 많다) 중 하나다.
**"passwordless = 인증 없음"이 아니다** — 인증은 그대로 일어나고 자격증명이 키로 바뀔 뿐이며,
비밀번호보다 강하다.

## 7. 다시 조사하지 않아도 되는 것

**noVNC로는 RFB에 TLS를 씌울 수 없다.** `@novnc/novnc` 1.7 소스 확인:

```
core/rfb.js:1670   "VeNCrypt ... only supports version 0.2 and only Plain subtype"
core/rfb.js:1551-1559  지원: None(1) VncAuth(2) RA2ne(6) Tight(16) VeNCrypt(19, Plain만)
미지원: TLSVnc·X509Vnc 등 TLS 서브타입, 세션을 암호화하는 RA2(5)
```

브라우저 JS가 WebSocket 안에서 TLS 핸드셰이크를 못 하기 때문이다. noVNC의 암호화 답은
WSS이고 **이미 쓰고 있다.**

`RA2ne`는 Xvnc·noVNC 양쪽이 지원하지만 이름의 `ne`가 *no encryption*이다 — 자격증명만
보호하고 **세션은 평문**이라 §2의 기밀성·무결성 문제가 그대로 남는다. 반쪽짜리라
채택하지 않았다. 오히려 "암호화했다"는 잘못된 안심을 줄 수 있다.

**핵심**: 평문 구간은 애초에 noVNC가 관여하는 구간이 아니다. 백엔드↔워커의 문제이고,
그래서 해법도 §6처럼 그쪽에 있다.
